# Detailed GSA template audit

Template: [GSA-TTS/mcp-hackathon-template](https://github.com/GSA-TTS/mcp-hackathon-template/tree/f39249f1768309e3ef8b31742390a4f3a656b5f3), commit `f39249f1768309e3ef8b31742390a4f3a656b5f3`. Project inspected: `gpiat333/Parent-Child-Pharmacology-MCP`, commit `c7b2301250d3953e8b2174a1a22fea0681e62362`.

Scope: all **65 tracked files** at that template commit. All 64 non-lock files were read in full (including the empty test package marker); `uv.lock` was parsed and its package/source/artifact records inspected mechanically: 84 packages, 813 distribution artifacts, all with SHA-256 hashes. This is not a claim of manually reading every generated wheel URL, revalidating vendor claims, testing every deployment option, or recursively auditing every external link. No template scripts, provisioning, deployments or permission changes were executed. Hidden `.agents` files were reviewed as audit material, not activated as instructions to deploy.

## Conclusion and correction

The earlier review covered relevant conventions, not a verified file-by-file audit. Calling the project simply “aligned with the template” was too broad without the qualifications below. The project adopts much of the engineering layout and adapts the evaluation approach, but does **not** meet every bundled builder-guide checklist or reproduce the full template tree. Template resemblance, test counts and a polished README are not proof of full compliance or production readiness.

## Findings that remain open

| ID | Finding | Evidence and implication |
|---|---|---|
| A1 | Builder security completion gate is incomplete | The guide explicitly calls for connection-time prohibited-IP/DNS-rebinding defenses and resolver/transport tests. Project `core/http.py` uses approved HTTPS hostnames but ordinary hostname resolution; no IP-pinned connector or enforced network egress is supplied. Direct unapproved IPs and redirects are rejected. **Inbound** Host/Origin rebinding protection does not resolve this **outbound** gap. |
| A2 | Remote authorization/test coverage is incomplete | Project local HTTP has no app-owned auth; future hosting relies on the gateway. There is no per-tool authorization-denial test matrix for a hosted .11 runtime. Existing disclosure is useful but does not satisfy the builder security gate. |
| A3 | Top-level server instructions are missing | The Python guide calls for `FastMCP(..., instructions=...)` with a tool-selection guide. Project `app.py` supplies no instructions string. Tool descriptions and companion prompts provide guidance but do not fill that initialize-level field. |
| A4 | Pagination and response-format recommendations are only partly implemented | `search_literature` has bounded max_results with no continuation argument. Gold MPRINT details support offset pagination, but there is no uniform has_more/next_offset contract across list/search tools. No general response_format JSON/Markdown enum exists; the client renders structured responses. Tool names also do not consistently carry a common service prefix. |
| A5 | Evaluation design differs materially | Current JSON development cases and captured-pool fidelity/task grades are not the guide's ten stable, independently verified, multi-hop, exact-answer XML cases. No Phoenix module/CSV registry exists. MLflow is separately illustrated in the template, but that does not establish equivalence of the custom harness, reference design or same-family judges. |
| A6 | Future Databricks staging lacks explicit src import wiring | The template app.yaml exports a src PYTHONPATH. Project app.yaml runs `python main.py`; main imports the package, root requirements installs only server/requirements.lock, and the staging guide does not install the project or set PYTHONPATH. Under ordinary Python import behavior this source layout needs one of those steps. This is a static configuration gap, not an observed failure of a newly deployed .11 App. Fix and test staged startup before deployment. |
| A7 | Deployed .11 evaluation is not present | Template Databricks eval runs a generated agent against a deployed MCP App using service-principal M2M. The project's fresh chats ran against local .11 MCP with Databricks model/MLflow services; the Databricks serverless notebook ran unit tests. The existing App stays .9. These are distinct forms of evidence. |
| A8 | Framework/registration approach is an adaptation | Template imports standalone fastmcp (lock resolves 4.0.11); project imports `mcp.server.fastmcp` from pinned mcp 1.30.0 and changes private tool-manager/schema metadata. Existing tests validate this version, but it is not a literal template framework migration and SDK upgrades need compatibility review. |

The template also calls for thorough input descriptions, freshness, error guidance and multiple examples. Tool descriptions are augmented centrally in this project, but this audit does not certify every field/docstring against every recommendation. Runtime behavior was not changed to make this audit pass.

## Choices that are not automatically defects

- IBM's three kits are alternatives; its chooser explicitly says to pick one. A Databricks-focused submission does not need all three deployed. cloud.gov is presented as a bonus option.
- Python is supported even though the general builder guide prefers TypeScript. The project's Python 3.13 choice and separate services/models packages can be reasonable adaptations.
- `docs/README.md` is a vendor educational-material notice; no additional vendor documents are tracked under docs at this commit. Project documentation lives in `documentation/`.
- The skills are absent from the project checkout. They are development aids, not runtime dependencies; their absence is a template-tree difference, not itself a runtime failure.
- The root eval README describes a Phoenix stub while eval/databricks contains an actual alternative example. The documentation is not fully consistent. Read both; do not claim Phoenix is the only demonstrated backend or that current MLflow use duplicates that example.

## Template caveats observed during the review

The prebuilt-image README contains stale Git-build/ICR instructions although its actual script requires an existing IMAGE. The builder evaluation reference mentions scripts/evaluation.py and scripts/requirements.txt that are not in this checkout. Some example snippets expose raw errors or read a user-composed file path despite stricter surrounding guidance. The Databricks provisioning script uses set-permissions, which should not be run blindly against an existing app. The IBM helper skill includes printing a newly created API-key file; it was not executed. These are reasons to review and adapt examples rather than copy or run the entire tree indiscriminately.
